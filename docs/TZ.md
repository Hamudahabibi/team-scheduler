## 2. Назначение и цели создания

### 2.1. Назначение

Система нужна киберцентру университета, чтобы составлять и вести недельное расписание тренировок нескольких команд с учётом:

- учебного расписания студентов (пары нельзя пропускать ради тренировок);
- личной доступности игроков (работа, дорога, личные дела);
- вместимости и часов работы компьютерных залов, которые команды делят между собой;
- требований тренера к тренировочному процессу (сколько тренировок в неделю, длительность, минимальный состав, отдых между тренировками).

### 2.2. Цели

1. Сократить время, которое капитан или тренер тратит на согласование расписания. Сейчас это опросы в мессенджере и ручной перебор вариантов, на одну неделю уходит 1–2 часа.
2. Исключить накладки: тренировки во время пар и превышение числа мест в зале.
3. Повысить посещаемость тренировок за счёт выбора времени, когда может прийти максимум игроков основного состава.
4. Накопить данные о посещаемости для анализа тренировочного процесса.

### 2.3. Критерии достижения целей

- Составление расписания на неделю для 5 команд занимает не больше 1 минуты вместе с проверкой результата администратором.
- В опубликованном расписании нет тренировок, пересекающихся с парами игроков основного состава, при условии, что они учтены в требованиях.
- В опубликованном расписании нет превышения вместимости залов: это гарантирует проверка в транзакции БД.

## 3. Характеристика объекта автоматизации

Киберцентр — университетское подразделение с одним или несколькими компьютерными залами. В нём тренируются студенческие команды по разным дисциплинам: MLBB, CS2, Dota 2, Valorant и другим.

Как устроен процесс сейчас:

1. Капитан создаёт опрос в Telegram или Discord: «кто когда может на этой неделе».
2. Вручную сводит ответы с расписанием пар, которое игроки присылают скриншотами.
3. Согласует время зала с администратором киберцентра, у которого свои таблицы.
4. Публикует итог в чате. Любое изменение запускает процесс заново.

Проблемы: ручной труд, ошибки при сведении, конфликты команд за зал, отсутствие истории посещаемости.

Особенности предметной области:

- Игроки — студенты разных групп и курсов, у каждой группы своё расписание пар. Оно меняется по неделям (числитель и знаменатель) и публикуется университетом.
- Команда состоит из основного состава (core) и запасных (substitute). Тренировку имеет смысл проводить, только если пришло не меньше заданного числа игроков основного состава (обычно 5 из 5 для MOBA и шутеров).
- Зал рассчитан на N мест (ПК), поэтому в нём одновременно могут тренироваться несколько команд, если хватает мест.

## 4. Требования к Системе

### 4.1. Роли пользователей

| Роль | Описание |
|---|---|
| Администратор (admin) | Сотрудник киберцентра. Управляет залами, учебными группами, командами, пользователями. Запускает генерацию расписания и публикует его |
| Тренер (coach) | Тренер или капитан команды. Управляет составом и тренировочным планом своей команды, отмечает посещаемость, смотрит доступность игроков |
| Игрок (player) | Студент. Указывает свою учебную группу и доступность, видит своё расписание тренировок и пар |

### 4.2. Функциональные требования

#### ФТ-1. Учётные записи и доступ

- ФТ-1.1. Самостоятельная регистрация игрока: e-mail, пароль, ФИО, учебная группа.
- ФТ-1.2. Вход по e-mail и паролю, выдача токена доступа с ограниченным сроком жизни, выход (отзыв токена).
- ФТ-1.3. Администратор назначает роли пользователям.
- ФТ-1.4. Каждый запрос к API проверяет права по роли и принадлежности к команде.

#### ФТ-2. Учебное расписание

- ФТ-2.1. Справочник учебных групп (например, «ИДБ-22-04»).
- ФТ-2.2. Импорт расписания группы из iCalendar (RFC 5545), включая повторяющиеся события (RRULE с FREQ=WEEKLY, INTERVAL, UNTIL, COUNT, EXDATE). Это покрывает чередование числителя и знаменателя.
- ФТ-2.3. Импорт расписания из JSON (список занятий с датой и временем) для источников без iCalendar.
- ФТ-2.4. Повторный импорт за тот же период заменяет занятия группы в этом периоде, без дублей.
- ФТ-2.5. Просмотр занятий группы за период.

#### ФТ-3. Доступность игроков

- ФТ-3.1. Игрок задаёт еженедельные интервалы доступности (день недели, время начала и конца) двух видов: «могу» и «предпочитаю».
- ФТ-3.2. Игрок добавляет исключения на конкретные даты: «не могу» (болезнь, сессия) или «могу» (поверх обычного правила).
- ФТ-3.3. Если игрок не задал ни одного интервала, считается, что он свободен всё время, кроме пар.
- ФТ-3.4. Перед парой и после неё автоматически добавляется буфер (настраивается, по умолчанию 10 минут).
- ФТ-3.5. Тренер видит тепловую карту доступности команды на неделю: сколько игроков основного состава свободно в каждый 30-минутный слот.

#### ФТ-4. Команды

- ФТ-4.1. Справочник дисциплин: название и размер основного состава.
- ФТ-4.2. CRUD команд с назначением тренера.
- ФТ-4.3. Управление составом: добавить или удалить игрока, роль в составе (core или substitute), игровая позиция.
- ФТ-4.4. Тренировочный план команды: количество тренировок в неделю, длительность, минимальное число игроков основного состава, допустимое окно времени в течение дня, минимальный отдых между тренировками, приоритет команды.

#### ФТ-5. Залы

- ФТ-5.1. CRUD залов с количеством мест.
- ФТ-5.2. Часы работы зала по дням недели.
- ФТ-5.3. Блокировки зала на интервал (мероприятие, ремонт, турнир).

#### ФТ-6. Генерация расписания

- ФТ-6.1. Администратор запускает генерацию на неделю для выбранных команд и выбирает алгоритм: жадный или метод ветвей и границ.
- ФТ-6.2. Результат генерации сохраняется как черновик (draft): список тренировок, значение целевой функции, статистика (сколько тренировок не удалось поставить и почему).
- ФТ-6.3. Генерация учитывает уже опубликованные тренировки других команд на эту неделю: они занимают места в залах.
- ФТ-6.4. Публикация черновика выполняется в одной транзакции: старые опубликованные тренировки этих команд на неделю отменяются, новые публикуются, вместимость залов перепроверяется под блокировкой.
- ФТ-6.5. Тренер или администратор может отменить отдельную тренировку.

#### ФТ-7. Просмотр и экспорт

- ФТ-7.1. Опубликованное расписание на неделю с фильтром по команде.
- ФТ-7.2. Личное расписание игрока: его тренировки и пары за неделю.
- ФТ-7.3. Экспорт расписания команды в формате iCalendar для подписки в календаре телефона.

#### ФТ-8. Посещаемость и аналитика

- ФТ-8.1. Тренер отмечает посещаемость тренировки: пришёл, опоздал, отсутствовал, уважительная причина.
- ФТ-8.2. Статистика посещаемости команды за период по каждому игроку.

### 4.3. Требования к алгоритму планирования

- Дискретизация времени — 30 минут, горизонт — одна неделя (336 слотов).
- Жёсткие ограничения:
  - тренировка лежит в окне плана и в часы работы зала;
  - на тренировке присутствует не меньше заданного минимума игроков основного состава, без пар и с учётом их доступности;
  - суммарная занятость мест в зале не превышает его вместимость ни в одном слоте;
  - между тренировками одной команды не меньше заданного отдыха и не больше одной тренировки в день.
- Мягкие критерии (целевая функция):
  - максимум ожидаемой посещаемости (основной состав с весом 1, запасные с весом 0,5);
  - попадание в предпочтительное время игроков;
  - равномерное распределение тренировок по неделе;
  - штраф за поздние тренировки.
- В первую очередь максимизируется число поставленных тренировок, во вторую — качество.
- Генерация для 10 команд и 2 залов укладывается в 5 секунд. У метода ветвей и границ есть лимит времени, по его истечении возвращается лучшее найденное решение.
- Результат детерминирован: одинаковые входные данные дают одинаковое расписание.

### 4.4. Нефункциональные требования

- Архитектура: backend-сервис с REST API в формате JSON. Клиентская часть (веб или бот) — отдельный этап, вне рамок этого ТЗ.
- Язык — Go, СУБД — PostgreSQL, миграции схемы версионируются в репозитории.
- Пароли хранятся только в виде bcrypt-хэша, токены доступа — в виде SHA-256-хэша.
- Все изменения, которые затрагивают несколько таблиц, выполняются в транзакциях.
- Структурированное логирование (JSON), корректная остановка по SIGTERM, проверка готовности (`/healthz`, `/readyz`).
- Конфигурация задаётся через переменные окружения.
- Запуск одной командой через Docker Compose.
- Покрытие тестами алгоритмического ядра — не меньше 80 %, интеграционные тесты хранилища на реальной PostgreSQL.
- Часовой пояс системы настраивается, по умолчанию Europe/Moscow.

## 6. Контроль и приёмка

- Автоматические тесты (unit и интеграционные) проходят в CI на каждый push.
- Сценарий приёмки: импорт расписаний трёх групп → создание двух команд и зала → ввод доступности → генерация → публикация → экспорт iCalendar → отметка посещаемости → статистика.
- Экспериментальное сравнение алгоритмов с таблицей результатов в docs/research.md.
