# team-scheduler

[![CI](https://github.com/Hamudahabibi/team-scheduler/actions/workflows/ci.yml/badge.svg)](https://github.com/Hamudahabibi/team-scheduler/actions/workflows/ci.yml)

Backend-сервис, который составляет недельное расписание тренировок киберспортивных команд университетского киберцентра. Система сама подбирает время с учётом трёх источников ограничений:

- **учебное расписание** — импорт пар групп из iCalendar с развёрткой повторений (числитель и знаменатель);
- **личная доступность игроков** — еженедельные правила «могу» и «предпочитаю» и исключения на даты;
- **залы** — число мест, часы работы, блокировки под мероприятия и тренировки других команд.

Проект выполняется в рамках магистерской ВКР «Исследование методов планирования тренировочного процесса киберспортивных команд и разработка информационной системы для автоматизации расписания».

## Возможности

- Роли администратора киберцентра, тренера и игрока, вход по токену.
- Команды, основной и запасной состав, тренировочный план микроцикла: тренировок в неделю, длительность, минимальный состав, окно времени, отдых, приоритет.
- Тепловая карта доступности команды на неделю.
- Генерация черновика двумя алгоритмами: жадным и методом ветвей и границ. Ответ объясняет, почему команде не хватило тренировок.
- Публикация в одной транзакции с проверкой вместимости залов. Две одновременные конфликтующие публикации не проходят обе.
- Личная неделя игрока (тренировки и пары) и выгрузка тренировок команды в календарь (`.ics`).
- Посещаемость и сравнение прогноза планировщика с фактической явкой.

## Как работает планирование

Неделя делится на 336 слотов по 30 минут, доступность каждого игрока — битовая маска `[6]uint64`. Для каждой команды перебираются все допустимые старты, где собирается нужный минимум основного состава и в зале есть места. Затем выбирается набор тренировок, максимизирующий целевую функцию:

```
ценность = Σ (M + приоритет · (100·посещаемость + 20·предпочтения − 15·поздно)) − 10 · (тренировки в соседние дни)
```

Большая константа M делает число поставленных тренировок важнее их качества.

| Алгоритм | Идея | Когда использовать |
|---|---|---|
| `greedy` | Раунды по командам, «самый ограниченный — первым», зал по принципу best fit | Повседневно: доли миллисекунды |
| `bnb` | Ветви и границы с жадным решением как рекордом, оценка по лучшим кандидатам в разные дни, лимит времени | При дефиците залов: на 2–3 п. п. больше тренировок |

Формальная постановка, обзор методов и результаты эксперимента — в [docs/research.md](docs/research.md).

## Стек

Go 1.27 (`net/http`, `log/slog`), PostgreSQL 17, [pgx](https://github.com/jackc/pgx), [goose](https://github.com/pressly/goose), bcrypt, Docker Compose, GitHub Actions, golangci-lint.

## Быстрый старт

```bash
git clone https://github.com/Hamudahabibi/team-scheduler.git
cd team-scheduler
BOOTSTRAP_ADMIN_EMAIL=admin@stankin.ru docker compose up -d --build
./scripts/demo.sh
```

`demo.sh` (нужны `curl` и `jq`) проходит сценарий приёмки из ТЗ: загружает расписания трёх групп из [examples/](examples), создаёт залы, команды и игроков, генерирует расписание обоими алгоритмами, публикует его и выгружает календарь.

Запуск без Docker:

```bash
docker compose up -d db
BOOTSTRAP_ADMIN_EMAIL=admin@stankin.ru make run
```

## Примеры запросов

```bash
API=http://localhost:8080/api/v1

# Вход
TOKEN=$(curl -s -X POST $API/auth/login \
  -d '{"email":"admin@stankin.ru","password":"demo-password"}' | jq -r .token)

# Импорт расписания группы на семестр
curl -X PUT "$API/groups/1/classes?from=2026-09-01&to=2026-12-31" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: text/calendar' \
  --data-binary @examples/idb-22-04.ics

# Черновик расписания на неделю методом ветвей и границ
curl -X POST $API/schedule/runs -H "Authorization: Bearer $TOKEN" \
  -d '{"week_start":"2026-11-09","algorithm":"bnb"}'

# Публикация
curl -X POST $API/schedule/runs/1/publish -H "Authorization: Bearer $TOKEN"
```

Полное описание API — [api/openapi.yaml](api/openapi.yaml) (OpenAPI 3.1, 50 операций).

## Структура

```
cmd/
  server/            точка входа сервиса
  experiment/        вычислительный эксперимент: сравнение алгоритмов
internal/
  config/            конфигурация из переменных окружения
  domain/            сущности и доменные ошибки
  timegrid/          неделя, слоты, битовые маски
  scheduler/         алгоритмы планирования (без ввода-вывода)
    synth/           генератор синтетических задач
  ical/              разбор и выгрузка iCalendar (RFC 5545)
  service/           сценарии использования и права доступа
  storage/postgres/  репозитории на pgx, транзакции, интеграционные тесты
  httpapi/           маршруты, middleware, JSON
migrations/          SQL-миграции (встроены в бинарник)
api/                 OpenAPI-спецификация
docs/                ТЗ, архитектура, исследование
examples/            примеры расписаний групп в iCalendar
scripts/             сценарий приёмки
```

## Разработка

| Команда | Что делает |
|---|---|
| `make test` | unit-тесты с `-race` |
| `make test-integration` | интеграционные тесты на PostgreSQL (каждый тест — во временной схеме) |
| `make cover` | покрытие |
| `make lint` | golangci-lint |
| `make experiment` | сравнение алгоритмов на синтетических задачах |
| `go test -bench . ./internal/scheduler/` | бенчмарки решателя |

Покрытие алгоритмического ядра — 97 %. Тесты планировщика проверяют все жёсткие ограничения независимой функцией, а не через код решателя.

## Конфигурация

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | — | Строка подключения к PostgreSQL |
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера |
| `TIMEZONE` | `Europe/Moscow` | Часовой пояс киберцентра |
| `BOOTSTRAP_ADMIN_EMAIL` | — | Пользователь с этим e-mail при регистрации получает роль admin |
| `TOKEN_TTL` | `168h` | Срок жизни токена |
| `CLASS_BUFFER_MIN` | `10` | Запас времени до и после пары, минут |
| `SOLVER_TIME_LIMIT` | `3s` | Лимит метода ветвей и границ |
| `LOG_LEVEL` | `info` | Уровень логирования |
